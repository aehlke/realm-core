# Separately linked Realm Core acceptance peers

This is a standalone CMake project with concrete targets `realm_admission_old` and `realm_admission_modern`. Configure it twice against two separate supplied SDK source roots and two output build directories outside both source roots. It never links two Core versions into one executable. The old build has no admission header or admission macro, and uses public Object Store Realm write APIs for immutable denial. The raw modern generic mutable peer uses in-Realm history, so unrelated history incompatibility cannot make its admission-denial case pass.

The old source root must be the pristine exact pin, verified by the execution owner from project pin/provenance. The modern source root must contain the complete staged candidate, including all Core changes. Do not modify package pins or installed SDK checkouts to create these roots. Use the approved isolated candidate process.

The expected old `src/realm/db.cpp` SHA256 from the staged preimage is `0fb13c17eda1110ad376088ae7105b03c333a17972423a4a38bd3737a5fc6634`. The expected modern SHA256 from the staged postimage is `398a8898e9e98f67716af5117e0aeb0317419b3d5fea056e3a500a10184210e3`. The coordinator must update the modern expected hash if implementation changes. These are file identities, not a substitute for checking the rest of the source tree. The generated manifests hash the relevant storage, Group, Object Store, and admission sources, and the runner rechecks them before executing.

Use the following configure/build invocations through the authorized Luna executor under the existing shared build/test admission lock, substituting absolute verified paths and exact revision/candidate identities. No invocation below has been executed by this source author. Keep all output in the task-owned evidence/build directories; do not place build directories inside either SDK source tree.

Retain exact configure arguments and stdout/stderr in the existing evidence log, verbose build/link output, both `CMakeCache.txt`, `compile_commands.json`, both generated `provenance-Debug.txt`, exact two executables, and `peer-evidence.json` or `peer-failure.json`. The runtime runner records executable and actual linked target-library hashes. A successful identity label alone is insufficient link provenance. The execution owner must inspect the verbose link commands and confirm each executable links only ObjectStore/Storage archives built from its corresponding supplied source root. Do not use an existing installed Realm library, modern nil configuration, or an unverified cached binary as the pristine old SDK.

Runtime acceptance is deterministic and bounded: each --hold owner emits READY only after a real committed write, remains alive until explicit release, and emits RELEASED only after releasing its actual Realm/DB. The special modern --retain owner opens and retains a real admitted Realm without a user write while an old immutable snapshot remains mapped. The runner holds two matching modern owners simultaneously, proves both writes are visible, fences nil/different/generic contenders until the last owner releases, tests each different cohort in both ownership orderings, tests pristine old/new in both orderings, and verifies fresh cohorts work after release. Every denial checks target bytes, inode/device, size, and nanosecond modification time. The pristine immutable peer uses public synchronous/asynchronous Realm APIs, verifies neither starts a write, and calls Group::write at the existing original to require FileAlreadyExists/create_Must without changing bytes/inode/mtime/schema/rows. The old immutable process can remain alive after verifying these refusals. Modern establishes real admitted DB ownership with --retain without changing that immutable snapshot; the same old process then drops its immutable Realm/DB/coordinator and attempts an ordinary mutable open, which must fail with incompatible-lock-file rather than a stale permissions-cache error. That modern owner also fences separately opened old ordinary and modern nil/different/generic mutable peers. Immutable readers are intentionally not counted as lifecycle/admission participants.

The runner never builds, changes source, edits pins, or deletes evidence. It cleans up only its own exact subprocess handles after bounded waits. Passing execution and build/link provenance remain required; this source-only deliverable does not claim either.

## Supported deployment scope and alias matrix

The admission contract is **ADVISORY SAME-COORDINATION-FILE mutable-session/lifecycle ownership**. Supported Reader and Shared participants across deployed versions use their fixed regular single-link app-group payload entries in the same entitled physical container and retain the same adjacent coordination inode. Parent-directory aliases are supported only when both the actual payload and its adjacent lock identity stay shared. This is a prospective deployment condition, not a finding that the old SDK rejected terminal aliases.

The pristine-old matrix above proves only ordinary same-path mutable fencing in both ownership orderings, plus the accepted immutable-reader boundary. **Unmodified old terminal-payload-alias writers can bypass the canonical adjacent lock; older lifecycle code that removes or replaces coordination files can split ownership. Neither is claimed fenced by this SDK.** These are ordinary legacy APIs, not reclassified malicious or raw writers. Deployments must audit or retire those incompatible participants and establish quiet lifecycle cutover where needed. No arbitrary-old-path guarantee, storage migration or policy ledger is supplied.

The additional modern matrix uses actual same, nil and raw generic DB entrypoints with a canonical admitted owner, requires typed ALIAS_DENIED before alias.lock creation, preserves target and canonical coordination witnesses, then attempts the inverse ordering with no canonical owner: the alias still cannot establish mutable ownership and a later canonical owner succeeds. A separately linked pristine-old ordinary canonical holder also refuses a modern guarded alias before effects. These cases supplement, and do not replace or weaken, the exact old same-path peer proof. The test runner deliberately does not expect an unmodified old alias contender to be denied.

Current/incoming/bootstrap/restore/replay payloads must be regular single-link nonterminal-link entries. Alias or unknown entry refusals preserve evidence and require explicit recovery; facts do not confer later write authority. Actual consuming lifecycle operations must retain their coordination locks through consumption and preserve those inodes. Explicit low-level externally synchronized lock-file deletion is outside this supported Reader contract; it is not made safe by an earlier inspection. Runtime/link/native qualification remains pending.
